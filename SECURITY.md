# Security policy

## Reporting

Report vulnerabilities privately through [GitHub's Report a vulnerability page](https://github.com/2youg1/sprawling-agents/security/advisories/new). Include the version or commit, platform, configuration, reproduction steps, impact and the boundary crossed. For execution reports, include the tool's confinement disclosure or `sprawling doctor` output. Use redacted examples and omit live credentials. Keep security-sensitive reports out of public issues, pull requests and discussions; use [public issues](https://github.com/2youg1/sprawling-agents/issues) for ordinary bugs.

There is no bug bounty. Public credit is optional: remain unnamed or choose a name or handle. We publish credit only with your consent.

## Trust and scope

sprawling runs under the local User's account. ACP agents the User adds and MCP tool servers execute their own code and are trusted components once added; a room or git worktree alone does not contain their access to the host. The city narrows how an ACP agent starts, not what it can do afterwards. Nothing in an agent's entry runs, not even a probe, before the User consents to the exact launch specification on its consent card: detection only reads other ACP clients' configuration files and the vendors' own directories. The city recomputes that specification's digest when the consent arrives and refuses a mismatch, so a changed card cannot change the command behind a consent already given. The digest has no key and is kept in `CONFIG.toml` beside the row it covers, and a row with no digest, like the built-in entry `[resident] harness` names, counts as written by the User; so the consent check guards against a card that changed, and the boundary against a writer is write access to `CONFIG.toml`. Adding an agent is a local-only verb. The agent starts without a shell, from the absolute path resolved at consent; an agent from the bundled catalog that `npx` or `uvx` starts runs the package version the catalog names. The city starts no login: an agent that asks for one is refused with the names of its login methods, the User signs in with the agent's own program, and the city does not read the tokens that program writes. An agent runs with the User's rights, including over the city: it can read the native key file described below and drive the city through it, including approving its own requests, and it can read the platform credential service. The kernel's gates and built-in file tools check write domains, reserved paths and read permissions. Those checks govern tool requests, not arbitrary code running under the account. An explicitly permitted `where: host` command runs with that account's access; its working directory does not restrict the paths it can reach.

Host-command confinement depends on the mechanism, platform and available prerequisites. Read the exec tool's disclosure for the run's selected execution route and its limits. `sprawling doctor` reports the machine's detected confinement and prerequisites, which may differ from a run's configured arm. The runtime's [confinement definition](crates/runtime/src/tools/exec/confinement.rs) describes its native and copied-tree arms; [execution boundaries](docs/operating.md#how-exec-is-confined) explain configuration and platform limits. A copied working tree alone does not restrict host reads, network access or credentials. Linux namespace confinement also exposes the host filesystem read-only outside the writable copy, so it does not protect the confidentiality of host files. Execution isolation applies to the command or guest, not to the whole sprawling process or external harness.

Configuration and records carry credential references. The Vault uses the platform credential service, with a disclosed session-memory fallback when its startup probe fails; non-empty configured environment credentials take precedence. The Linux platform backend is a kernel keyring cleared on reboot; Windows Credential Manager and macOS Keychain retain stored keys across reboots. Read the reported custody lifetime rather than assuming disk persistence. The city removes every `SPRAWLING_SECRET_*` variable and `SPRAWLING_PAIRING_TOKEN` from the environment of each program it starts, so an agent, an MCP server, a resident's browser or a host command does not inherit the city's environment credentials; on Windows those programs also start without the city's console window, so they cannot read its screen buffer. One program keeps the city's environment on purpose: the city a supervising parent restarts. The handler that opens the User's own browser for `/web` follows the same rule as every other program the city starts, with its standard input and output closed, because the browser it starts can outlive the city; on Windows the city starts that handler as `cmd.exe` under the `SystemRoot` that the protected installation record names, and `icacls.exe` the same way, never by a bare name that the binary's own folder could answer. Plaintext is available in process memory and at authorized provider and tool authentication sinks. Credential state shown to clients does not return stored values, but the Vault does not isolate secrets from trusted code or every process running as the same account. Secret scanning cannot detect every credential format.

The city binds to loopback by default; a listener beyond loopback with no configured pairing token mints one for that serve, keeps it in the key file, and prints it once in the banner of a city served without a console. Every caller presents a credential, on loopback as on an exposed listener, and the listener checks a request in layers before any credential is read. A `Host` header that is not one of the listener's own names is refused, which stops DNS rebinding. A WebSocket upgrade or a POST whose `Origin` is not one of the listener's own origins, port included, is refused before the upgrade, and so is the `null` origin; a listener on every interface admits only the origin of the host the request was sent to. A request whose `Sec-Fetch-Site` is present and is not `same-origin` is refused; a CORS preflight is refused, and no response carries an `Access-Control-*` header. A browser credential is never a cookie, so no browser attaches one on its own: the page keeps a non-exportable Ed25519 device key in its own origin's storage and signs a challenge to obtain a session token that lives only in the page's memory. The first browser is paired through a one-time open code that `/web` delivers in a file only the User's account can read; another browser types the pairing code the terminal shows, and each code takes one guess, at most one guess per second across the listener. Because every judged guess replaces the code, any process on this machine that sends a browser's `Origin`, and any host that reaches an exposed listener, can keep the code changing with one wrong guess a second, and can push a page's pending challenge out by asking for new ones; neither reveals a credential, and the open code that `/web` delivers still pairs. A limit per source would not stop this: every local process arrives from the same loopback address, and one shared code taking one guess is what keeps guessing slow. A session token is good while a socket holds it and for 60 seconds after the last one closes. Forgetting a device ends its session tokens and closes every socket that holds one; a socket greeted with the native key is not a device's and stays open. The paired browsers' public keys are kept in the city's `.sprawling/browsers.toml` and read when the city starts, so write access to the city directory is enough to add a device. A native client on this machine reads a key file in the per-user runtime directory, created readable only by the User's account and deleted when the city closes in order; a city that is killed leaves it behind, and the next serve on that port replaces it. The client reads that file only when `--at` names a loopback address or `localhost`, and asks for `--token` for any other host, so a mistyped host never receives this machine's key. It finds the file by port and does not check which program answers on that port: after a killed city, another program on this machine that takes the port receives the key. A minted key is useless once its city has stopped; a configured `SPRAWLING_PAIRING_TOKEN` is not, so a city run with one is closed in order rather than killed. Responses carry a Content Security Policy with `frame-ancestors 'none'`, and `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy` headers. A resident's browser tool, and the User's own browser when a resident drives it, is refused the city's own origins. These credentials control access to city interfaces. They do not encrypt the listener's HTTP/WebSocket transport, and they do not contain a hostile process running as the same account, which can read the key file and the credential store.

The separate remote door authenticates paired devices with watch or act permissions, refuses commands classified as local-only, and seals session frames end to end. The route that serves the browser page is trusted to deliver it unchanged: a route that replaces the page can read what the page reads. See [remote access](docs/operating.md#reaching-the-city-from-another-device) for deployment and device permissions.

Report unauthorized network access, breaches of enforced file or credential boundaries, and behavior exceeding a supported configuration's actual isolation. Prompt injection or a trusted tool carrying out an explicitly permitted action alone does not establish a bypass; identify the unauthorized effect. Prior local write access is not a new vulnerability unless sprawling grants that access or crosses a further protected boundary.
