# Security policy

## Reporting

Report vulnerabilities privately through [GitHub's Report a vulnerability page](https://github.com/2youg1/sprawling-agents/security/advisories/new). Include the version or commit, platform, configuration, reproduction steps, impact and the boundary crossed. For execution reports, include the tool's confinement disclosure or `sprawling doctor` output. Use redacted examples and omit live credentials. Keep security-sensitive reports out of public issues, pull requests and discussions; use [public issues](https://github.com/2youg1/sprawling-agents/issues) for ordinary bugs.

There is no bug bounty. Public credit is optional: remain unnamed or choose a name or handle. We publish credit only with your consent.

## Trust and scope

sprawling runs under the local User's account. ACP agents the User adds and MCP tool servers execute their own code and are trusted components once added; a room or git worktree alone does not contain their access to the host. The city narrows how an ACP agent starts, not what it can do afterwards. Nothing in an agent's entry runs, not even a probe, before the User consents to the exact launch specification on its consent card; the city recomputes that specification's digest when the consent arrives and refuses a mismatch, so a catalog refresh cannot change the command behind a consent already given. Adding an agent and starting its login are local-only verbs. The agent starts without a shell, from the absolute path resolved at consent, with its version pinned. Its login is the agent's own program, and the city does not read the tokens it writes. <!-- v0.0.11-verify --> An agent runs with the User's rights, including over the city: it can read the native key file described below and drive the city through it, including approving its own requests, and it can read the platform credential service. The kernel's gates and built-in file tools check write domains, reserved paths and read permissions. Those checks govern tool requests, not arbitrary code running under the account. An explicitly permitted `where: host` command runs with that account's access; its working directory does not restrict the paths it can reach.

Host-command confinement depends on the mechanism, platform and available prerequisites. Read the exec tool's disclosure for the run's selected execution route and its limits. `sprawling doctor` reports the machine's detected confinement and prerequisites, which may differ from a run's configured arm. The runtime's [confinement definition](crates/runtime/src/tools/exec/confinement.rs) describes its native and copied-tree arms; [execution boundaries](docs/operating.md#how-exec-is-confined) explain configuration and platform limits. A copied working tree alone does not restrict host reads, network access or credentials. Linux namespace confinement also exposes the host filesystem read-only outside the writable copy, so it does not protect the confidentiality of host files. Execution isolation applies to the command or guest, not to the whole sprawling process or external harness.

Configuration and records carry credential references. The Vault uses the platform credential service, with a disclosed session-memory fallback when its startup probe fails; non-empty configured environment credentials take precedence. The Linux platform backend is a kernel keyring cleared on reboot; Windows Credential Manager and macOS Keychain retain stored keys across reboots. Read the reported custody lifetime rather than assuming disk persistence. The city removes every `SPRAWLING_SECRET_*` variable and `SPRAWLING_PAIRING_TOKEN` from the environment of each program it starts, so an agent, an MCP server, a browser or a host command does not inherit the city's environment credentials; on Windows those programs also start without the city's console window, so they cannot read its screen buffer. <!-- v0.0.11-verify --> Plaintext is available in process memory and at authorized provider and tool authentication sinks. Credential state shown to clients does not return stored values, but the Vault does not isolate secrets from trusted code or every process running as the same account. Secret scanning cannot detect every credential format.

The city binds to loopback by default; a listener beyond loopback with no configured pairing token mints one for that serve and prints it once. Every caller presents a credential, on loopback as on an exposed listener, and the listener checks a request in layers before any credential is read. A `Host` header that is not one of the listener's own names is refused, which stops DNS rebinding. A WebSocket upgrade or a POST whose `Origin` is not exactly the listener's own origin, port included, is refused before the upgrade, and so is the `null` origin; a request whose `Sec-Fetch-Site` names another site is refused; a CORS preflight is refused, and no response carries an `Access-Control-*` header. A browser credential is never a cookie, so no browser attaches one on its own: the page keeps a non-exportable Ed25519 device key in its own origin's storage and signs a challenge to obtain a session token that lives only in the page's memory. The first browser is paired through a one-time open code that `/web` delivers in a file only the User's account can read; another browser types the pairing code the terminal shows, and each code takes one guess, at most one guess per second across the listener. A native client on this machine reads a key file in the per-user runtime directory, created readable only by the User's account and deleted when the city closes. Responses carry a Content Security Policy with `frame-ancestors 'none'`, and `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy` headers. A resident's browser tool, and the User's own browser when a resident drives it, is refused the city's own origins. <!-- v0.0.11-verify --> These credentials control access to city interfaces. They do not encrypt the listener's HTTP/WebSocket transport, and they do not contain a hostile process running as the same account, which can read the key file and the credential store.

The separate remote door authenticates paired devices with watch or act permissions, refuses commands classified as local-only, and seals session frames end to end. The route that serves the browser page is trusted to deliver it unchanged: a route that replaces the page can read what the page reads. See [remote access](docs/operating.md#reaching-the-city-from-another-device) for deployment and device permissions.

Report unauthorized network access, breaches of enforced file or credential boundaries, and behavior exceeding a supported configuration's actual isolation. Prompt injection or a trusted tool carrying out an explicitly permitted action alone does not establish a bypass; identify the unauthorized effect. Prior local write access is not a new vulnerability unless sprawling grants that access or crosses a further protected boundary.
