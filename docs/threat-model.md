# Threat model

sprawling runs a city under one User's account. This model follows data and authority across the city's interfaces, from clients and external services to tools and local storage. See [SECURITY.md](SECURITY.md) for private reporting and report scope.

## Assets and trust assumptions

| Asset | Where it crosses a boundary | Security property |
|---|---|---|
| Client identity and session authority | Per-user native key, browser device keys and session tokens, remote-device keys and watch or act grants | Admit the intended principal and scope the authority of the session. |
| Provider and connector credentials | Configuration holds references. The Vault, process memory and the configured authentication sinks handle plaintext. | Keep values out of ordinary configuration, records and client views. Limit their handling to authorized sinks. |
| User and model data | Prompts, attachments, tool arguments and results cross into providers, connectors, harnesses and the client | Apply the configured routing, read and egress rules. Keep model-controlled content inert when displaying it. |
| Authority over actions | Client commands, tool admission, execution placement and ACP launch consent | Require the authority and placement that apply to the requested action. |
| Persistent city state | Ledger bytes and chain head, CAS objects, browser device registry and city configuration | Detect corruption where verified. Preserve city configuration and authority records within the User's filesystem boundary. |
| Build and release inputs | Rust and client dependency manifests, lockfiles and shipped client assets | Enforce dependency, source, license and advisory policies at the build boundary. |

Two actors are first-class. A **prompt-injected model** can ask for actions and emit arbitrary text through its granted interfaces. Tool output, retrieved documents and peer descriptions can supply its instructions. The city relies on gates and capabilities to bound actions even when the model follows those instructions. A **same-account local process** can use the account's access to the native key and may reach its credential service or writable city state. This model evaluates that actor explicitly. The controls on city interfaces do not confer OS isolation between processes owned by the same account.

An unpaired web page, an unauthenticated network peer, an overprivileged tool request, and a corrupt or unexpected input at an advertised boundary are in scope. A compromised OS or administrator can replace the executable or inspect its memory, so OS integrity is an assumption. A deliberately trusted provider may see everything sent to it, and a deliberately launched local ACP harness or stdio MCP server runs its own code with the User's rights. Isolation against that host code and confidentiality against the intended recipient are outside the guarantees here. Deployment also assumes control of the build inputs and of the route that serves the remote browser page.

## Cryptographic inventory

The remote browser and Rust city must agree on the door protocol. The gateway's file Vault implements a local passphrase backend. The serving custodian currently selects the platform credential service or session memory, so the file backend has no production open path. Each AEAD is fixed at its own interface. The browser-facing interface uses AES-GCM and the file format uses ChaCha20-Poly1305. The budget row names below refer to `Tools/xtask/budgets.toml`. ## Keeping the model current

When a boundary or control changes, update the row, production call site and evidence together. Document known gaps in the same boundary table.

Put each full module path or repository-relative file path in its own pair of backticks. Use forward slashes and ASCII letters, digits, underscores, hyphens and dots in file paths. A path with a directory and a dot in its filename can use any extension. A bare name needs a recognized suffix, such as those for scripts and lockfiles, or a conventional filename such as `justfile`. To cite a named Rust test or Lean theorem or lemma, append two colons and the declaration's short name within the same backticks.

`cargo xtask gates spec` checks whether those references resolve. A resolving reference establishes existence alone. It does not establish control effectiveness, test applicability or complete coverage. The on-demand mutation job answers a different question about how selected tests respond to implementation changes. `cargo xtask gates docnum` checks the figures pulled from the performance register.
